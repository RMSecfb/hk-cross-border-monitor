# 港股跨境交易監控（HK Monitor）

GitHub Actions 每 30 分鐘抓取全部港股（約 2,800 檔）的 1 分鐘 K 線（Yahoo，延遲約 15 分鐘），
產生黃/橙/紅警報，結果以「日期時分秒」檔名存回本 repo 的 `data/`，並以 Streamlit 儀表板呈現。
共 **12 條規則**：量能類 5、價格類 6、市場機制類 1。

門檻最初取自《港股交易風險監控即時系統_Excel模組》的「異常交易監控參數」「VCM與市場機制」，
但多條已依實測刻意偏離 Excel（收市競價紅燈 8%→2.5%、VCM 兩條併一條、3 分鐘量暴增整條重寫），
原因與證據一律記在 `docs/監控指標調整規劃.md`，該文件是指標定義與沿革的唯一出處。

```
GitHub Actions（雲端，可連 Yahoo / HKEX）
  ├─ 盤中監控  每 30 分鐘 → data/snapshot、data/alerts、data/status.json
  ├─ 盤後批次  16:42      → data/daily、data/report、data/stats、data/quality、
  │                         data/profile、config/universe.csv
  │                         ＋ 1 分 K 與同時點基準上傳 GitHub Releases
  ├─ 每週股本  週六        → config/shares.csv
  ├─ 補跑報告  手動        → 指定期間重算盤後報告
  └─ 重建基準  手動        → 由 Release 既有 1 分 K 重算同時點基準並上傳
        │ commit 回 repo
        ▼
  本 repo ──► Streamlit 儀表板（streamlit_app.py）
          │     ├─ 看盤中／盤後警報、VCM、高風險排行、趨勢追蹤
          │     ├─ 下載 Excel／PDF 監控報告
          │     └─ 線上改參數、手動啟動盤中抓取（回寫 GitHub，需 Secrets）
          └─► 公司電腦 git pull 後由其他系統讀取 data/
```

## 一、批次設定

1. repo → **Actions** → 選「盤後批次」→ **Run workflow**，會下載監控名單（HKEX 證券名單、VCM 名單）與約半年日線，建立 `data/stats`。
2. repo → **Actions** → 選「每週更新股本」→ Run workflow，建立 `config/shares.csv`，才會計算換手率。
   取的是 `sharesOutstanding`（在港上市股數），A+H 兩地上市公司不會用總股本當分母；全港股約需 1–2 小時。
3. 之後盤中、盤後會自動依排程執行。想在非交易時段測試：Actions →「盤中監控」→ Run workflow，勾選 force。

## 二、排程（香港/台北時間；cron 以 UTC 撰寫）

| 工作 | 時間 | 說明 |
| --- | --- | --- |
| 盤中監控 | 10:02、10:32、11:02、11:32、12:17、13:32、14:02、14:32、15:02、15:32、16:02 | 午休不跑；避開整點以減少 GitHub 排程延遲 |
| 盤後批次 | 16:42 | 以收盤資料全量重算；盤中失敗時以盤後報告為準 |
| 每週股本 | 週六 10:00 | 選用 |
| 補跑歷史盤後報告 | 手動 | 補跑指定期間：重算盤後報告、累積 1 分 K 歷史並上傳 Release。同時點基準不在這裡算，交給當天盤後批次或「重建同時點基準」統一重算 |
| 重建同時點基準 | 手動 | 由 Release 上既有的 1 分 K 重算基準並上傳，不抓 Yahoo（約 2–3 分鐘）。平常由盤後批次自動完成，補跑完歷史或基準算錯時手動補發一次 |

**補跑的硬限制**：Yahoo 1 分鐘資料只保留 **30 天**，過期無法補救。又因量能規則要湊滿
逐檔天數閘門，封存起點（2026-10-05，`bars_20261002` 從未存在且已確認永久補不回來）
使得「3 分鐘量暴增」「連續放量」真正可用是 **2026-10-08** 起、「成交量暴增」是 10/16 起。
**補跑任何早於 2026-10-12 的日子，這兩條規則會因分母湊不滿而整條靜默，結果比原報告更差**
（10/09 實測：182 筆→0 筆、86 筆→0 筆，已還原回原版）。詳見規劃書 1.3。

- 假期、颱風不需設定：程式以盈富基金（2800）當日有無行情判斷，無行情即結束。
- GitHub 排程可能延遲數分鐘到數十分鐘，偶爾跳過一次；下一次執行會重抓全天資料，不會漏算。
- 用量估算：每次盤中約 3–6 分鐘 × 11 次 × 22 日 + 盤後約 10 分鐘 × 22 日 ≈ 1,000–1,700 分鐘/月，
  在私有 repo 免費額度 2,000 分鐘內。實際時間請到 Actions 頁面查看，再調整 `.github/workflows/intraday.yml` 的 cron。

## 三、資料檔（`data/`）

| 路徑 | 更新 | 內容 |
| --- | --- | --- |
| `status.json` | 盤中每次 | 最近一次執行時間、資料截至時間、取得檔數、抓不到的代碼、新增警報數 |
| `snapshot/YYYY-MM-DD/snapshot_YYYYMMDD_HHMMSS.parquet` | 盤中每次 | 每檔一列：現價、前收、漲跌幅、5 分鐘漲跌、VCM 門檻與使用率、累計量、量比、偏離 MA、成交額 |
| `alerts/alerts_new_YYYYMMDD_HHMMSS.csv` | 盤中每次（有新警報時） | 本次新增警報 |
| `alerts/alerts_YYYYMMDD.csv` | 盤中每次 | 當日累計警報（`found_at` = 發現批次） |
| `report/eod_alerts_YYYYMMDD.csv`、`eod_summary_YYYYMMDD.csv` | 盤後 | 以收盤資料重算的全日警報（逐筆）與統計 |
| `report/eod_report_YYYYMMDD.csv` | 盤後 | 預警列表（Excel 格式）：預警ID、時間、等級、代碼、名稱、監控類型、指標值、閾值、觸發次數、風險分數、連續上榜、近5日上榜、操作建議 |
| `report/score_YYYYMMDD.csv` | 盤後 | 每檔每日風險分數、連續上榜天數（趨勢追蹤用） |
| `daily/YYYY/daily_YYYYMMDD.parquet` | 盤後 | 日線（每天一檔，只新增不覆寫） |
| `stats/stats_YYYYMMDD.csv` | 盤後 | 隔日盤中用的基準，13 欄：`code`、`prev_close`、`ma`、`avg_vol`、`avg_turnover`、`halted`、`halt_run_5`、`halt_run_20`、`ex_div`、`split_recent`、`split_unadjusted`、`shares`、`shares_src` |
| `quality/quality_YYYYMMDD.json` | 盤後 | 1 分 K 加總 ÷ 日線量的分布（中位、p05/p95、>2 倍與 <0.5 倍檔數），只記錄不改判斷 |
| `profile/profile.csv` | 盤後 | 各 30 分鐘時段每分鐘均量。**已不參與任何指標計算**，僅保留歷史（舊的 30 分鐘時段內插分母已移除，見第四節） |

警報欄位：`time, code, rule, level, value, detail, name, found_at`

**1 分 K 存放於 GitHub Releases，不進 git 歷史**（git 歷史不會因刪檔而縮小，commit 進 repo 會以每年
約 0.47 GB 永久累積）。每個交易日一個 `bars-YYYYMMDD` 標籤，內含當日 `bars_YYYYMMDD.parquet`
與同時點基準 `baseline_YYYYMMDD.parquet`，保留 30 天後由 workflow 自動刪除。盤中批次只下載基準檔一個。
寫入時與 Release 既有檔**合併而非覆寫**（曾因覆寫損毀過兩天的日線，見規劃書九之四）。

repo 容量：快照保留 30 天（`config/settings.yaml` 的 `keep_snapshot_days`），每日新增約 2–3 MB，一年約數百 MB。

## 四、監控規則（閾值在 `config/rules.yaml`）

| 規則 | 依據 |
| --- | --- |
| 即時漲跌幅、偏離均線、開盤價異常 | 現價/開盤 vs 前收、MA20。開盤價異常只取 09:30 後 `open_window_min` 分鐘內的第一根 K 線 |
| 1 分鐘、5 分鐘急漲急跌 | 1 分鐘 K 線逐分鐘回溯；5 分鐘以「5 分鐘前最後成交價」為參考。**兩者的過期門檻是獨立參數**：1 分鐘用 `max_prev_gap_min`（3 分鐘），5 分鐘用 `max_ref_gap_5m_min`（8 分鐘＝規則本身的 5 分鐘＋同樣的 3 分鐘緩衝） |
| 成交量暴增、3 分鐘量暴增、連續放量 | 分母一律是「過去 N 個交易日同一時點」的量（成交量暴增 20 日、其餘 5 日），由盤後算好的基準檔提供。**某檔歷史不足就不計算該指標，不會退回別的算法**——舊的 30 分鐘時段內插分母已移除（它是 3 分鐘量暴增 98% 觸發率的來源）。成交量暴增與 3 分鐘量暴增採 A（熱門）／B（冬眠）雙軌，倍數門檻相同、成交額下限不同。3 分鐘量暴增與連續放量每批次每檔只報最嚴重一筆 |
| 冬眠股異動（盤後） | 當日成交額 ÷ max(截至前一交易日的 20 日均成交額, 1 萬)。**刻意不經過 1 分 K**——最冷門的股票當天可能一根 1 分 K 都沒有，日線對全名單永遠是滿的。只看冬眠股（20 日均成交額 < 50 萬）且當日成交額 ≥ 100 萬，與成交量暴增不重疊 |
| VCM 預警 | `\|5 分鐘偏離\|` ÷ 該股 VCM 門檻（HKEX 名單 ±5/10/15/20%）；黃 80%、橙 90%、紅 100%（紅＝已達交易所熔斷門檻）。排除各時段首 15 分鐘與尾市 20 分鐘；午市不沿用早市參考價。原「VCM 觸發（模擬）」與「VCM 內部預警」已合併為此單一規則 |
| 收市競價異常（盤後） | 收市價 vs 16:00 前最後價。三閥門：最後成交距 16:00 超過 30 分鐘降一級；依 20 日均成交額分一般股／冷門股兩套門檻，冷門股的橙紅另需 CAS 金額或占比條件；偏離 > 5%（CAS 的結構上限）判為資料異常不給等級 |
| 換手率異常（盤後） | 日線成交量 ÷ 在港上市股數，需 `config/shares.csv` |

### 適用範圍

| 條件 | 參數 | 適用規則 |
| --- | --- | --- |
| 當日成交額 ≥ 100 萬 | `min_turnover_hkd` | 1 分鐘／5 分鐘急漲急跌、即時漲跌幅、開盤價異常 |
| 20 日均成交額 ≥ 1,000 萬（活躍股） | `active_min_avg_turnover_hkd` | **連續放量、偏離均線** |
| A／B 雙軌（分池門檻 1,000 萬） | `pool_split_turnover` | **成交量暴增、3 分鐘量暴增**——A 軌當下累計成交額 ≥ 100 萬、B 軌 ≥ 500 萬 |
| 20 日均成交額 < 50 萬（冬眠股） | `dormant_move.max_avg_turnover` | 冬眠股異動 |
| 逐檔天數閘門 | `min_hist_days`（5）、`min_hist_days_cum`（10） | 3 分鐘量暴增／連續放量需 5 個交易日、成交量暴增需 10 個 |

**注意 3 分鐘量暴增不是活躍股限定**——它與成交量暴增一樣走雙軌，B 軌刻意涵蓋冬眠股
（冬眠股突然短時爆量正是拉抬的典型樣態）。只有連續放量與偏離均線是活躍股限定。

### 排除與標記

**價格類指標排除最近一個交易日沒有成交的股票**（`halted`）——那時 `prev_close` 是過期價格，
比出來的跳空是假的。量能類不排除，改在「備註」欄標記。

| 標記文字 | 旗標 | 掛在哪些規則 |
| --- | --- | --- |
| `近 5 / 20 個交易日內曾停牌` | `halt_run_5`、`halt_run_20` | 量能類（5 日：3 分鐘量暴增、連續放量；20 日：成交量暴增） |
| `除息日` | `ex_div` | 價格類 |
| `近期曾股份分割（分母未還原）` | `split_recent` | 3 分鐘量暴增、連續放量、成交量暴增、換手率異常 |
| `近期分割且歷史價未還原（均線／均額橫跨斷點）` | `split_unadjusted` | 偏離均線、冬眠股異動 |
| `股本為A+H合計（換手率偏低）` | `shares_src` | 換手率異常（取不到在港股數而退回 A+H 合計者，分母偏大、數值偏低） |

兩組分割標記互斥，因為失真來源不同：第一組是**分母**未還原（1 分 K 封存存的是當時的未還原
成交量、`shares.csv` 是靜態股本）；第二組是**歷史價**未還原（Yahoo 絕大多數分割都已回頭還原
歷史價，少數例外會讓 `ma`／`avg_turnover` 橫跨斷點，以「記錄比例 vs 實際價格比」對帳判定）。
**日線價格不做任何還原**——曾誤判為未還原並回頭還原，當天即回退（見規劃書九之五）。

**停牌判定**以「名單 × 交易日」格線進行：某格「沒成交」= 該格整列缺席，**或**列存在但 `volume == 0`
（Yahoo 兩種表示法都用過，只認後者會漏抓數百檔）。`halt_run_*` 需「曾連續 ≥ 3 天沒成交」
（`halt_tag_days.run_min`），零星單日無成交是冬眠股常態而非停牌。換手率異常與冬眠股異動
**不做**停牌標記（前者分母是靜態股本、不經歷史均值；後者的低均額正是它要衡量的訊號本身）。

### 冷卻與門檻修改

冷卻時間：同股票、同規則、同等級在冷卻期內只報一次（`cooldown_min`）；全日型規則另以
「每檔取最後一筆」收斂，實測同股同級一天只會出現一次。

修改閾值有兩種方式，擇一即可：在 Streamlit 的「參數」頁直接改（會寫回 GitHub 並留下修改人與原因，見第五節），
或直接編輯 `config/rules.yaml`。兩者的 commit 紀錄都是完整變更軌跡。

**門檻處理原則**：倍數門檻一律維持上線時的現行值，不得為了降低筆數而縮放區間——區間縮了
就可能漏掉真的有問題的標的。唯二例外是經證實結構上不可能觸發者（收市競價紅燈 8%、
VCM 模擬觸發），那屬設定錯誤而非待校準。

## 五、Streamlit 儀表板

1. 到 https://hk-cross-border-monitor.streamlit.app/ 
2. repo 每次有新 commit，Streamlit 會自動更新；頁面上的「重新整理資料」按鈕可清除快取。
3. 參數修改會寫回 `config/rules.yaml`、`config/actions.yaml`（保留註解），並在 `config/param_log.csv` 留下修改人、原值、新值、原因；
     commit 紀錄即為完整軌跡。下一次排程執行即套用新參數。

側欄顯示現在時間、最近一次盤中抓取、前次/下次排程與今日排程表。排程時間直接讀 `.github/workflows/*.yml`，
在 GitHub 上修改 cron 後頁面自動同步。

頁面：警報（含盤中報告下載）、VCM 監控（依 VCM 使用率由大到小排序）、今日高風險排行、個股查詢、
盤後報告（預警列表、可回溯日期、報告下載）、趨勢追蹤（連續異常標的、風險變化排行、近 10 日上榜次數）、參數。

**監控摘要**：警報頁與盤後報告頁的最上方（表格之前）各有一塊摘要，盤中與盤後各自獨立。
預設以規則組出當日統計敘述（不需任何 API）；若已設定 `GROQ_API_KEY`，可按「AI 分析」改用 Groq
生成帶判斷的分析摘要，按「規則摘要」可切回。AI 僅在按下按鈕時呼叫，不會在每次重新整理時自動計費。
模型不寫死：每次先向 Groq 查詢該金鑰目前可用的模型，依偏好順序挑選（`llama-3.3-70b-versatile` →
`openai/gpt-oss-120b` → `openai/gpt-oss-20b` → `llama-3.1-8b-instant`），避免 Groq 下架模型後功能失效；
失敗時會顯示 Groq 回傳的原因並自動退回規則摘要。

**報告下載**：警報頁與盤後報告頁各有「下載監控報告」。按「產生報告檔」後可下載 Excel 與 PDF，
兩者版面一致：**摘要文字 → 統計 → 規則分布 → 明細表**，摘要放在所有表格之前；
若先按過「AI 分析」，報告帶入的就是 AI 版摘要。產生器在 `report_export.py`，盤中盤後共用。

| | 盤中報告（警報頁） | 盤後報告（盤後報告頁） |
| --- | --- | --- |
| 資料 | 當日累計警報，依等級排序 | 預警列表，風險分數由高到低 |
| Excel | 全部等級、全部列、全部欄位 | 全部等級、全部列、全部欄位 |
| PDF | **只列紅燈與橙燈**的前 200 列 | 前 200 列的重點欄位 |

PDF 之所以縮減，是因為 A4 寬度有限：盤中黃燈多（常占半數以上），盤後 13 個欄位全放會把每列擠成多行。
完整內容一律在 Excel。盤中 Excel 資料量大（上萬列約需 10–20 秒），所以改為按鈕觸發，不在每次重新整理時重算。

風險分數 = 各監控項目當日最高等級加總（紅 40、橙 25、黃 10，上限 100）。
兩個門檻分開設定，目前同為 **60**：`list_min_score`（60）決定是否「上榜」進入盤後預警列表；
`streak_min_score`（60，即至少紅+橙或兩個紅）決定是否進入趨勢追蹤的「連續異常標的」，
需連續 `streak_days`（預設 3）個交易日都達到。兩者都可在參數頁修改。

> `list_min_score` **於 2026-10-29 由 30 調為 60**：30 分只需一個紅燈即達標，實測日均 165 檔
> 上榜，風控桌無法消化；60 分 ≈ 一紅一橙或兩橙一黃，日均 62 檔，並與 `streak_min_score` 對齊
> （兩者不一致時，「上榜」與「連續異常」的母體不同，難以解讀）。

盤後預警列表排序：風險分數由高到低 → 同一檔股票排在一起 → 等級（紅/橙/黃）→ 監控類型。
操作建議依規則類別 × 等級設定於 `config/actions.yaml`。

## 六、限制

- Yahoo 港股報價延遲約 15 分鐘，非官方 API，雲端主機可能被限流或缺資料；`status.json` 的 `missing` 列出抓不到的代碼。
- VCM 預警以 1 分鐘收盤價計算，會漏掉分鐘內的瞬間尖峰，且無法區分自動對盤與整數買賣單位，為內部計算值，不等同交易所實際觸發紀錄。
- 停牌判定由日線推得（整列缺席或 `volume == 0`，以交易日格線計算），非官方停牌公告；
  冬眠股的零成交日與真停牌在日線上無從區分，故以「曾連續 ≥ 3 天沒成交」收緊。
- **Yahoo 沒有記錄的公司行動抓不到也無法自動修正**（例如 2723 於 2026-10-06 的 10 倍價格斷點，
  Yahoo 無任何分割紀錄）。曾試以「開盤價是否跳空」判別，20 筆樣本中 13 筆誤判，**不可用**；
  要真正修好需要交易所公告這類權威來源。
- 掛撤單、自成交、帳戶盈虧等客戶層面規則需內部委託/成交資料，不在本 repo 範圍。
- 沽空異常尚未納入（HKEX 沽空報表格式待確認後加入）。
- 量能三指標需要 1 分 K 歷史：某檔累積不足（新上市、長期停牌）就不計算，報表上不會出現該檔的
  量能警報。`data/status.json` 的 `baseline_days` 與 `volume_rules` 可看出當批次是否有分母可用
  （`volume_rules` 是兩態旗標，「計算中」代表有分母）。**1 分 K 封存已於 2026-10-29 取消收錄門檻，
  改為全名單收錄**，但股票從線下升到線上還要再等 5 或 20 個交易日才有分母，
  剛從冬眠轉活躍的那 1～4 週仍會靜音——「冬眠股異動」就是為補這段空窗而加的。
- **封存起點 2026-10-05，`bars_20261002` 永久缺失**，故 09/30～10/07 的歷史報告在量能三指標上
  是空的，那代表「沒有分母可算」而非「那幾天沒有異常」。拉歷史分布時把這幾天算進母體會低估觸發率。
- 行情僅供內部風控使用，repo 與 Streamlit 都必須設為私有。
